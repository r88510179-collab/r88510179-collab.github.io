# Pool Alerts — deployment (owner-approved steps only)

Nothing below has been done to production. Each **[APPROVAL]** step changes production and needs your explicit release
authorization. Keep this order: database first (recording starts, nothing is sent), sender second (sending stays off),
phone acceptance third, then turn sending on and merge the app.

## Automated release (recommended): GitHub Actions → **Pool Alerts release**

`release.mjs`, run by `.github/workflows/pool-alerts-release.yml`, performs sections 1–6 below for you, checks each
step and writes a scrubbed evidence report (workflow artifact, kept 90 days). It works from a phone: Actions → Pool
Alerts release → Run workflow → choose the operation and target, type the confirmation `<operation>-<target>`.

| Operation | What it does | Changes |
| --- | --- | --- |
| `preflight`, `status`, `verify` | Neon identity (project, branch, endpoint, database, owner role), catalog state against the release manifest, sender health/version/environment, trigger, branch headroom and compute used; `verify` also checks the catalog is the final reviewed one and whether the site serves this commit's alert client | nothing |
| `backup` | a branch `backup-before-pool-alerts-YYYYMMDD-<commit>` of the production branch (reused if it exists) | backup branch |
| `stage` | backup, then migrations 006 and 007, each with a fingerprint guard **inside its own transaction** (it commits only as the reviewed catalog, otherwise nothing is committed), environment marker, a new sender password generated by Neon, owner/status tokens derived from the control key and the monitor token from the separate monitor key (the sender stores only digests; production refuses to stage without the monitor key), the exact reviewed bundle, waits until health, status and the owner token answer four times in a row (old and new instances overlap after a deployment) and the monitor token reads status but is refused on owner routes, the baseline cycle (nothing historical is announced), the hourly trigger. **Group sending stays off.** Safe to run again: each step looks first | database, sender, trigger |
| `activate` | refuses unless an Android phone and an iPhone each have a passed device check whose alert was also opened (Maintenance Center → Pool Alerts operations), then turns group sending on | sending on |
| `pause` / `resume` | group sending off / on | sending |
| `adopt-tokens --owner-sha256 … --status-sha256 … [--monitor-sha256 …]` (staging only, command line) | the staging sender learns the digests of your tokens (the Maintenance Center's key setup shows them, computed in your browser; digests are not secrets), so staging connects to your keys before this workflow is on `main` | staging sender configuration |
| `rollback --level pause\|trigger\|sender\|database` | pause; disable the trigger; switch the deployment off; remove 007 then 006 with the rollback files, each guarded by the fingerprint it must restore (needs a backup branch from the last 7 days) | as named |

## 0. Preconditions

- The release PR's CI is green (NFL Pool Tests incl. `push-alerts-isolated`, Pool Alerts Browser Acceptance).
- You have the reviewed commit SHA and the bundle SHA-256 from CI (`push-alerts-isolated` job summary).
- A trusted computer with Node.js 22 (and optionally the Neon CLI, or `curl` with a Neon API key).

## 1. Backup **[APPROVAL]**

Neon Console → project **NFL Pool** → Branches → Create branch from `main` named
`backup-before-pool-alerts-YYYYMMDD` (no compute needed). The Free plan allows 10 branches; 7 exist today, so this
fits. Record its id with your release notes.

## 2. Database migration **[APPROVAL: production migration]**

Neon Console → **NFL Pool** → SQL Editor, database `nfl_pool`, role **nfl_pool_owner**:

1. Paste and run the whole of `nfl-pool/migrations/006-pool-alerts.sql`. It refuses any other role and a second run.
2. Run, in the same editor:
   ```sql
   INSERT INTO pool_alerts.environment (name) VALUES ('production');
   ```
3. Verify (expect `1 | 1 | f | 5`):
   ```sql
   SELECT (SELECT count(*) FROM pool_alerts.settings),
          (SELECT count(*) FROM pg_trigger WHERE tgname = 'nfl_pool_alerts_capture'),
          (SELECT sending_enabled FROM pool_alerts.settings),
          (SELECT count(*) FROM pg_tables WHERE schemaname = 'public');
   ```

From now on publications are recorded; nothing is sent (no sender yet, and sending is off).

## 3. Keys and the sender login **[APPROVAL]**

On the trusted computer: `node nfl-pool/push/ops.mjs keys`. It prints a VAPID key pair, the owner token, the status
token (with their SHA-256 digests) and a database password. Save them in your password manager. Then in the SQL Editor
(role nfl_pool_owner):

```sql
ALTER ROLE pool_alerts_sender LOGIN PASSWORD '<database password from ops keys>';
```

### 5a. Change a setting later (config-only redeploy)

Send only the variables that change; the bundle is reused. Behavior verified on the staging function:

- Variables **merge** with the previous deployment. A variable you leave out keeps its value. To turn the deployment
  switch off, send it with an empty value: `{"POOL_ALERTS_SENDING": ""}`; to turn it on again, `"enabled"`.
- The change reaches requests once running instances are replaced: within about a minute (0–36 s on staging). For an
  immediate stop use **Pause sending** (database switch), which applies to the very next request.

```sh
printf '%s' '{"POOL_ALERTS_SENDING": ""}' > change.json   # example: deployment switch off
curl -sS -X POST "https://console.neon.tech/api/v2/projects/patient-thunder-85353337/branches/br-late-hat-b55ygmj4/functions/poolalerts/deployments" \
  -H "Authorization: Bearer $NEON_API_KEY" -F "environment=<change.json"
rm change.json
node nfl-pool/push/ops.mjs health    # repeat until it shows the change ("sendingConfigured": false here)
```
